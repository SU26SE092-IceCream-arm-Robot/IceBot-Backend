# Requirements Traceability Matrix — IceBot Backend

**Document type**: Team-facing traceability matrix (working draft). Maps every FR/NFR in `deliverables/02_srs/srs.md` back to `functional_inventory.md`/`database_inventory.md` evidence, and forward to the underlying inventory rows and data entities, so the team can review completeness and confidence per requirement.

**Source basis**: `deliverables/02_srs/srs.md` (requirement text, Related/Evidence/Status fields), `deliverables/00_repo_evidence/functional_inventory.md` (inventory rows), `deliverables/00_repo_evidence/database_inventory.md` (entities/constraints), `deliverables/00_repo_evidence/repo_truth_map.md` (architecture-level evidence for cross-cutting NFRs). No `src/` or `docs/` files were modified to produce this matrix, and `project_introduction.md`/`srs.md` were not modified.

**Scope note**: This is a many-to-one matrix at FR/NFR granularity (matching `srs.md`'s own consolidation of 260 `functional_inventory.md` rows into 133 FRs), not a one-row-per-inventory-ID matrix. `srs.md` §1.1 and §8.6 flag a formal one-row-per-inventory-ID matrix as a separate, more granular follow-up artifact not produced here. Every `functional_inventory.md` ID is reachable through the FR listed as its consolidator (verified in the prior review pass — see `srs.md` §4 for the full ID list per FR).

## Status column semantics

Per the task's fixed vocabulary (`Supported`, `Inferred`, `Assumption`, `Unclear`, `Needs Review`), each row's Status is derived from `srs.md`'s own Status field for that requirement, as follows:

- **Supported** — `srs.md` states the requirement is directly code-evidenced (its Status field begins with "Supported"). This means *statically code-evidenced*, not runtime/test-verified — see `srs.md`'s top-of-document Status legend; no test-execution evidence backs any row in this matrix.
- **Inferred** — evidence is indirect (naming/wiring/sibling-pattern match rather than a full line-by-line read), or `srs.md` marks the claim `[Inferred]` as its primary qualifier.
- **Assumption** — the requirement rests on an `[Assumption]` explicitly marked in `srs.md` (e.g., current-deployment-default claims that are not binding product requirements).
- **Unclear** — `srs.md`'s Status field is itself "Unclear" or the requirement's core mechanism was not settled by static reading.
- **Needs Review** — `srs.md` marks the requirement (or a materially incomplete part of it) `Partial`, or no `functional_inventory.md`/`database_inventory.md` evidence was found for a claim during this matrix pass. This is the closest fit to the task's "no clear evidence → Needs Review" instruction, extended to cover known-incomplete features so the team has a single column to scan for outstanding work.

Where `srs.md` lists a compound status (e.g., "Supported (X); Inferred (Y)"), the table below uses the first-listed word as the row Status and records the qualifier in Notes — this keeps the matrix traceable to `srs.md`'s own wording rather than introducing a new judgment call.
