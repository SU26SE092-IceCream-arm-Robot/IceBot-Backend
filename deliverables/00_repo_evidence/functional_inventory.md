# Functional Inventory

This document is a repo-evidence-based inventory of the functional capabilities of the IceBot Backend. It is built per `deliverables/DELIVERABLES_AGENT.md`: source priority is code in `src/`, then `docs/` source-of-truth documents, then `ARCHITECTURE.md`/`AGENTS.md`, then clearly marked inferred assumptions. No files under `src/` or `docs/` were modified to produce this document.

## Methodology

- Coverage is organized by the bounded contexts defined in `docs/DOCUMENTATION_COVERAGE.md` (Identity, Tenants, Catalog, Sales Catalog, Orders, Payments, Devices, Inventory, Robot Configuration, Production Configuration, Production Packages, Edge Integration, Operations, Sync) plus a cross-cutting runtime section (SignalR, GraphQL, Dashboard).
- Every row was produced by directly reading the cited controller, application handler, domain entity, or documentation file — not inferred from naming alone. Where a claim rests only on file presence/wiring rather than a full read, this is noted in the row's Status cell or in the Notes section.
- **Status** values:
  - `Implemented` — working code wired end-to-end (route/consumer → handler → domain/persistence).
  - `Partial` — code exists but is incomplete, stubbed, or narrower than what documentation describes.
  - `Documented-only` — described in `docs/` but no matching code was found.
- Where the same underlying capability is reachable from two entry points that were surveyed by different research passes (e.g. a GraphQL read that duplicates a REST read, or an order-dispatch action described both from its controller and from its EdgeIntegration internals), the capability is listed once in its most natural owning section, with a cross-reference note rather than a duplicate row.
- IDs (e.g. `IDN-01`) are stable short codes per bounded context, intended to support a future requirements traceability matrix.

## Notes, Ambiguities, and Open Questions

Per `deliverables/DELIVERABLES_AGENT.md`, items below are flagged rather than resolved by inference.

**Identity / Tenants / Devices**
- IDN-15b (temporary-password onboarding without invitation): the code path exists (`CreateInternalAccountCommandHandler` sets `Password` directly when `LocalLoginEnabled && !CreateInvitation && InitialPassword` is provided), but `docs/api/IDENTITY_ONBOARDING_RULES.md` states this variant's surrounding lifecycle (forced password change, restricted first-login access) is "not part of the current contract." Classified `Partial` for that reason.
- DEV-09/DEV-08 (`ReplaceDeviceCommandHandler`, `RetireDeviceCommandHandler`) reach into the Inventory bounded context to transactionally rebind/retire dispenser topology (see INV-05); the Devices-side behavior was verified directly, the Inventory-side invariants are covered separately under INV-05.
- `UpdateDeviceTypeCommandHandler`, `SetDeviceTypeStatusCommandHandler`, `UpdateDeviceModelCommandHandler`, and several read-only query handlers (`GetDeviceQueryHandler`, `ListDevicesQueryHandler`, `GetExecutionEndpointQueryHandler`, `ListExecutionEndpointsQueryHandler`) were confirmed via controller wiring and doc description rather than full line-by-line reads; classified `Implemented` with lower confidence than directly-read rows.
- `docs/architecture/MULTI_TENANCY_RULES.md` states the REST `tenantTree` route was intentionally removed in favor of GraphQL-only (TEN-21) — confirmed against code, no conflict.

**Catalog / Sales Catalog / Inventory**
- INV-08 (dispenser consumption) and INV-14 (inventory readiness evaluator) are domain/service-layer capabilities verified directly in code, but their callers live in the Orders/EdgeIntegration execution pipeline (INV-08) and the Production Configuration deployment gate (INV-14, see PC-10) respectively — outside the Catalog/SalesCatalog/Inventory controllers themselves.
- INV-13 (inventory summary) exists only as a GraphQL query; there is no equivalent REST endpoint in `ManagementInventoryController`.
- `ManagementProductOptionsController`/`ManagementProductTemplateOptionsController` and `ManagementRecipesController`/`ManagementProductTemplateRecipesController` are near-duplicate controllers (tenant product vs. global template) sharing the same command handlers via a `ProductManagementCommandScope.IsGlobalTemplate` flag — treated as one feature per capability rather than doubled.
- Delete handlers for OptionGroup/ProductOption were confirmed via controller signatures and cross-referenced against sibling Create/Update patterns rather than opened line-by-line; classified `Implemented` by pattern consistency.

**Orders / Payments / Operations**
- `CreatePaymentSession` and `GetOrderPaymentStatus` are routed through `OrdersController` but documented under Payments (PAY-01, PAY-02) since they operate on `PaymentTransaction`/PayOS.
- All Orders management **read** capabilities (list/detail orders, overview, fulfillment queue, status histories, execution-attempt summaries) are GraphQL-only (ORD-12 to ORD-18); the REST `ManagementOrdersController`/`ManagementExecutionAttemptsController` expose only write actions plus one diagnostics GET (ORD-11).
- `PaymentMethodCatalogHostedService` (startup seeding of the PayOS payment method row) is infrastructure bootstrap plumbing, not a user-facing feature, and is intentionally excluded from this inventory.

**Robot Configuration / Production Configuration / Production Packages**
- No Documented-only rows were found in these three contexts — every documented lifecycle stage (authoring/import, deployment/rollback, installation/upgrade) had direct code backing.
- RC-19's `RobotArtifactTechnicalContractFeature`, PP-16's `ProductionPackageUpgradeReconciliationService`, and PC-12's `DeploymentFailureNotificationFeature` were confirmed via wiring/registration and call-site behavior rather than a full line-by-line read of every internal method.

**Edge Integration / Sync / Cross-cutting**
- MQTT-02 (edge uplink consumer) and the equivalent REST endpoints (IOT-01 to IOT-04, IOT-07, IOT-09) share identical Application-layer handlers — confirmed by reading both the MQTT dispatcher and the REST controllers, not inferred from naming.
- SYNC-05 (sync dead-letter retry) is scoped to `ExecutionReport.*` event types only; other event families can be resolved/ignored (SYNC-06, SYNC-07) but not automatically replayed — classified `Partial`.
- DEV-15 (MQTT credential provisioning REST surface) and MQTT-04 (its backing provisioner) were confirmed from different research passes; the controller route itself (`ManagementExecutionEndpointsController`) was read directly for DEV-15, while MQTT-04 is evidenced primarily by the provisioner class and `docs/operations/MQTT_OPERATIONS.md`.
